# v0.5.0 + v0.6.0 設計メモ

> **リリース時の補足 (2026-07-14)**: 実際には両者を **v0.5.0 に統合して 1 リリース** で publish した。以下の「v0.6.0」への言及は設計時点の計画であり、実装はすべて v0.5.0 に含まれる。

> 逆引き API（v0.5.0）と検証ヘルパ（v0.6.0）を **1 ブランチで同時に実装** する際の設計判断・スコープ・未決事項を記録。

## 背景

`docs/v0.4.0-roadmap.md` で予定していた以下を、houki-egov-mcp Phase 2 / houki-nta-mcp v0.10 系の実需要に応じて前倒し実装する:

- **v0.5.0**: 逆引き API（`lookupByLawId` / `lookupByLawNum` / `getAllNames`）
- **v0.6.0**: 検証ヘルパ（`isValidLawId` / `validateAllEntries` / `extractLawNames` + CI スクリプト）

ルーティング API（`routeToMcp` / `resolveWithRouting`）は YAGNI 判断で延期（3 つ目の MCP 着手時に再評価）。理由: 現状 `resolveAbbreviation(...).source_mcp_hint` で十分捌けるため。

## v0.5.0 逆引き API

### `lookupByLawId(law_id: string): AbbreviationEntry | null`

e-Gov `law_id` から辞書エントリを引く。

- **インデックス**: `Map<string, AbbreviationEntry>` を **lazy 構築**（最初の呼び出し時）
- **対象**: `entry.law_id !== null` のエントリのみ（`null` は除外、null をキーに lookup できないため）
- **大文字小文字**: 完全一致（e-Gov の `law_id` は仕様上すべて大文字英数字なので、normalize なし）
- **重複**: 仕様上 `law_id` は一意。重複があれば validateAllEntries が検出する

```ts
lookupByLawId('363AC0000000108');  // → 消費税法エントリ
lookupByLawId('321CONSTITUTION');  // → 日本国憲法エントリ
lookupByLawId('999XX0000000000');  // → null
```

### `lookupByLawNum(law_num: string): AbbreviationEntry | null`

法令番号（漢数字表記）から辞書エントリを引く。

- **インデックス**: `Map<string, AbbreviationEntry>` を lazy 構築
- **対象**: `entry.law_num !== undefined` のエントリのみ
- **正規化スコープ**: v0.5.0 では **完全一致のみ**。漢数字↔算用数字の正規化（`normalizeLawNum`）は別 issue として後送り
- **理由**: 漢数字正規化は `三百八十二` のような大きな数の表記、`一千` vs `千` の揺れなど、独立した設計領域。本パッケージのスコープでは控えめに

```ts
lookupByLawNum('昭和六十三年法律第百八号');     // → 消費税法エントリ
lookupByLawNum('昭和63年法律第108号');           // → null（v0.5.0 では正規化しない）
```

> **未決**: `normalizeLawNum` を将来追加するなら `src/normalize.ts` に置くか別モジュールか。memory `houki_abbreviations_v04_roadmap.md` のオープン課題 §4 を参照。

### `getAllNames(name: string): string[]`

任意の `abbr` / `formal` / `aliases` から、そのエントリの **全別表記** を返す。

- **入力**: `abbr` / `formal` / `aliases` のいずれか
- **出力**: `[abbr, formal, ...aliases]` の重複除去・順序保持済み配列
- **見つからなければ空配列**（`null` ではなく `[]`、配列演算がそのまま使える）

```ts
getAllNames('消法');
// → ['消法', '消費税法', '消費税', 'インボイス', 'インボイス制度', ...]

getAllNames('存在しない');
// → []
```

**用途**: LLM プロンプトで「この法令の全表記」を列挙する。例えば「`消費税法` は `消法` `インボイス制度` `軽減税率` などの呼称でも参照される」と LLM に伝えるシナリオ。

## v0.6.0 検証ヘルパ

### `isValidLawId(law_id: string): boolean`

e-Gov `law_id` の **形式** が妥当かを純粋関数で判定する。外部 API は叩かない。

#### 認識するパターン

データ実例から以下のパターンを認識:

| パターン | 例 | 説明 |
|---|---|---|
| `^\d{3}(AC\|CO\|IO\|MO\|RU)\d{10}$` | `363AC0000000108` | 標準: 元号(1)+年(2)+種別(2)+連番(10) |
| `^\d{3}CONSTITUTION$` | `321CONSTITUTION` | 憲法専用 |

種別コード:
- `AC` = Act（法律）
- `CO` = CabinetOrder（政令）
- `IO` = ImperialOrdinance（勅令）
- `MO` = MinisterialOrdinance（省令）
- `RU` = Rule（規則）

> **未対応の種別**: e-Gov の bulk data には他にも `DF` 系（例: `105DF0000000337`）、`M\d{2}` 形式の省令系（厚労省令 = `M60` 等）が存在することが houki-egov-mcp の `csv-parser.ts` コメントから確認されている。ただし正確な構造（`M` 直後の桁数、種別コード一覧、特殊形式の有無）が未確定のため、v0.6.0 では **辞書に実エントリが存在する種別のみ** 厳格に判定する保守的方針で開始する。新種別を辞書に追加する際は、本パッケージ側でパターンを拡張する v0.6.x が必要。

```ts
isValidLawId('363AC0000000108');  // true
isValidLawId('321CONSTITUTION');  // true
isValidLawId('AAA');              // false
isValidLawId('');                 // false
```

### `validateAllEntries(): ValidationReport`

辞書全体の **静的整合性** をチェックする。CI で `npm run validate` のように呼ぶ想定。

#### チェック項目

| 検査 | レベル | 内容 |
|---|---|---|
| `abbr` 重複 | error | `abbr` は family 全体で一意であるべき |
| 必須フィールド欠損 | error | `abbr` / `formal` / `domain` / `category` / `source_mcp_hint` のいずれか欠損 |
| `law_id` 形式不正 | error | `law_id !== null` なのに `isValidLawId` が `false` |
| `law_id` 重複 | error | 同じ `law_id` が複数エントリに付いている |
| `category` × `source_mcp_hint` 不整合 | warning | `law` なのに `source_mcp_hint='houki-nta'` など |
| `aliases` の重複 | warning | 同一エントリ内で重複、または別エントリの `abbr` と衝突 |

戻り値:

```ts
interface ValidationReport {
  valid: boolean;        // errors.length === 0
  errors: ValidationIssue[];
  warnings: ValidationIssue[];
}
interface ValidationIssue {
  code: string;          // e.g. 'duplicate_abbr', 'invalid_law_id'
  message: string;
  entry?: AbbreviationEntry;  // 該当エントリ（特定できる場合）
}
```

#### category × source_mcp_hint の対応表

```ts
const CATEGORY_HINT_MAP: Record<Category, SourceMcpHint[]> = {
  constitution:           ['houki-egov'],
  law:                    ['houki-egov'],

  rule:                   ['houki-egov'],
  'kihon-tsutatsu':       ['houki-nta', 'houki-mhlw'],
  'kobetsu-tsutatsu':     ['houki-nta', 'houki-mhlw'],
  'qa-jirei':             ['houki-nta'],

  saiketsu:               ['houki-saiketsu'],
};
```

### `extractLawNames(text: string, options?): LawNameMatch[]`

入力テキスト中の **法令名らしき文字列** を辞書マッチで抽出する。

- **アプローチ**: 全エントリの `abbr` / `formal` / `aliases` を検索キーとし、`text.indexOf` で線形走査
- **データ規模**: 174 件 × 平均 3 キー ≒ 500 候補。N=500、入力テキスト 1KB 程度なら実用的に高速
- **重複処理**: 同一エントリが複数箇所にヒットしたら全部返す（呼び出し側で dedup できる）
- **オーバーラップ**: `民法` と `民法等の一部を改正する法律` のような部分包含は **長い方を優先**

```ts
interface LawNameMatch {
  entry: AbbreviationEntry;
  matchedKey: string;     // 'abbr' / 'formal' / 'aliases' のいずれかの値
  position: number;       // text 内の開始 index
  length: number;         // matchedKey の長さ
}

interface ExtractOptions {
  /** 最小マッチ長（デフォルト 2、ノイズ抑制） */
  minLength?: number;
  /** 重複エントリを除去（同じ entry.abbr のものを 1 件に絞る、デフォルト false） */
  dedupe?: boolean;
  /** 部分包含時に長い方を優先（デフォルト true） */
  preferLonger?: boolean;
}
```

> **既知の限界**: 文脈解析はしない（純粋な文字列マッチ）。「民法 の解釈は…」と「民法人 の認可は…」のような文脈区別は呼び出し側で行う。

### CI スクリプト `scripts/verify-law-ids.mjs`

e-Gov API を叩いて **`law_id` ↔ `formal` / `law_num` の一致** を CI で検証する。

- **入力**: 辞書全件（`law_id !== null` のもの）
- **API**: `houki-egov-mcp` が利用するのと同じ e-Gov 法令 API（`https://laws.e-gov.go.jp/api/...`）
- **出力**: 不一致レポート（CI が失敗したらアラート）
- **頻度**: 週次 GitHub Actions workflow（既存の `.github/workflows/ci.yml` には含めず、別 workflow `verify-law-ids.yml` を作る）
- **本パッケージ本体には含めない**: `scripts/` 配下の Node スクリプトとして配置、`npm run verify-law-ids`
